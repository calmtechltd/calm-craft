## Findings by classification

### R1 — Target schema/design gap, C1/C4: define malformed revision behavior before tightening it

Actual boundary: `convex/research.ts:221–294`. `expectedRevision` currently uses `v.number()`, then exact equality with the run revision (`:255–265`). The command key is constrained by `semanticKey` through `acceptCommand`/`persistCommand` (`convex/lib/commands.ts:89–105`, `shared/command-identity.ts:22–26`). There is no explicit `Number.isSafeInteger(expectedRevision) && expectedRevision >= 0` check at this facade. An ordinarily invalid fractional/negative revision will mismatch and produce the recorded stale/no-effect result; an invalid key fails the owning command validator before insertion.

The draft correctly calls the safe-integer rule an **input adoption requirement** and says it is not established by primitive declarations. The supplied governing specs require an exact current version, but do not prescribe this new malformed-input partition.

Consequence: adding the validator could change whether a malformed request throws, returns a classified held result, or consumes an idempotent command key. That is an observable API decision even though the added check is sensible internal hardening.

Scoped remedy: before implementation/acceptance, specify the malformed-revision outcome and whether validation occurs before command intent or yields a durable no-effect receipt. Preserve duplicate command semantics for requests already accepted. Do not label current `v.number()` a contract violation, and do not infer that stale refusal is an implemented semantic validator.

### R2 — Missing effect-sufficiency evidence, C3; the draft appropriately avoids declaring a defect

Actual recovery predicate: `convex/lib/researchExecution.ts:280–317`. It iterates current plus previous command IDs, reads a linked effect, and refuses absent receipts or `reserved`/`uncertain` spend. It also requires same-business exact assignment-research worker job/run, rejects queued/running/uncertain workers, and caps attempts below three. It does not itself explicitly reject missing/foreign commands/effects, an uncertainty receipt paired with misleading resolved accounting, or missing accounting. `convex/lib/researchContinuation.ts:30–66` has stricter explicit relation/receipt/spend checks.

That textual difference alone is **not a reachable defect**. Native `resolveSpend` couples exact effect receipt status with paid accounting in one mutation (`convex/lib/budgets.ts:410–465` and subsequent allocation updates). Worker admission/overdue-effect handling retains uncertainty and prevents ordinary admission (`convex/lib/programmeWork.ts:818–946`); registered provider paths also reauthorize. Raw schema allows optional spend/effect relationships more broadly than the intended host paths. Corrupting records directly in a fixture would prove the predicate's behavior, but not that a customer or normal host transition can produce the dangerous combination.

Consequence: current source supports the ordinary settled path, but does not establish that all misleading/missing relation combinations are impossible or harmless at replacement admission. C3 cannot be marked verified based on these selected tests or on a shorter predicate being conventional.

Scoped remedy: prove actual reachability/exclusion across the owning effect/accounting/worker paths and recovery facade; if reachable, fix under Foundation B7 and Lead Research B3 rather than weakening the proposed rule. Keep the original command/effect lineage and costs. This is the same unresolved sufficiency question the draft explicitly retains; no new accepted exemption is inferred.

### R3 — Verification scope limit, C2/C3/C4/C5: selected test titles do not prove every recovery path

Read actual assertions in `convex/researchExecution.test.ts:325–362,398–446,487–530,564–590,709–769`. These are meaningful tests for retained malformed qualification, explicit resume without reacquisition, saved paid results during pause, stop-time original crawl retention, public business/revision/pause refusals, first receipt replay, and a command-bound wake.

The selected case at `:487` tests **`continueResearch`**, not `recoverResearch`, for evaluator unavailability/uncertain paid start. It therefore does not directly prove recovery predicate refusal for uncertain historical effects. The public case at `:709` checks the real control facade and retained wake identity but does not exercise rollback on a failed transaction. None of these inspected cases directly demonstrates the failed/cancelled/timed-out **second** retained provider job reset, or all future-authority/version combinations, or worker exhaustion at three.

The draft reports six tests passed elsewhere. This audit did **not** rerun them or inspect its linked evidence/JSON, so that run remains a supplied claim, not fresh independent verification. The draft honestly lists additional exit evidence and explicitly disclaims broad/live/deployed acceptance; its test claims should remain attributed and bounded.

Scoped remedy: when authorized execution is available, reuse relevant existing cases, then select meaningful checks for the specific unproven branches. Do not add tests merely to mirror code or fabricate unreachable corruption as a production regression. Maintain separate evidence for native transactions and for classified policy behavior.

## Verified static observations supporting the draft

- **Current facade coverage:** `control` independently authenticates the signed-in business, loads `researchOwner`, accepts the typed action command, returns the first receipt for duplicate identity, checks current domain revision/action state, and combines readiness/recovery gates. Generic journey controls refuse lead-research control (`convex/lib/journeys.ts:835–840`), so they do not bypass this operation.
- **Helper authority is contextual:** trusted helper callers are public `get/control`, bounded `researchMaintenance`, private fixture `researchDiagnostics`, and isolated tests. They have materially different envelopes. The draft explicitly distinguishes these rather than claiming `recoverResearch` alone independently authorizes user recovery. `researchOwner` (`convex/lib/leadResearch.ts:76–96`) validates kind, business, authorized source, assignment/lead/programme/campaign relation. `researchFence` (`:97–153`) covers stop, assignment policy, pause, current versions/qualification policy, authority and recipients. `assignmentFence` (`convex/lib/recipientSafety.ts:40–91`) applies programme/campaign stop before pause/version controls. No arbitrary client-authored executable input is added.
- **Finite service path:** `researchMaintenance.ts:287–303` recovers only declared prerequisite failure categories after its retry time and readiness, then reloads the owned run. The helper rejects worker attempts at three (`researchExecution.ts:298–304`). Private diagnostic recovery is tied to a fixture-owned sourcing assignment (`researchDiagnostics.ts:31–50`); it is not an alternative customer facade.
- **Exact retained stage:** `recoverResearch` (`researchExecution.ts:318–370`) updates the retained worker/run. Ordinary qualification recovery retains acquisition, command history, costs and candidates. For acquisition number two with an exact retained providerJobId and failed/cancelled/timed_out final crawl, it resets the same crawl outcome/pollCount and saved stage; it does not submit a new job. `researchNext` (`:20–25`) permits read-only original submitted-job polling before general controls. Source placement proves the branch's intent and identity retention; execution success remains unproven here.
- **No new continuation authority:** targeted acquisitions/new qualification versions are in `researchContinuation.ts` and use stricter lineage and settled-effect admission. C2's original second-job polling branch does not authorize a third acquisition or a new provider invocation. It is reasonable to keep that explicit branch within checkpoint recovery while requiring its coverage before acceptance.
- **Atomic public coordination:** helper worker/run writes, domain revision increment, retained wake and `completeCommand` run in the one native public mutation. `programmeCoordinator.ts:81–94` admits a recovery wake only for exact retained business/programme/run revision and a committed `recovered` receipt. This agrees with C4's proposed preservation boundary, though no forced rollback/concurrency test was run. Internal maintenance runs under its existing coordinator scheduling envelope; it is not required to invent a user control receipt.
- **Safe feature inspection:** `research.get` validates exact assignment/lead/campaign relation, derives `canRecover/recoveryBlocker`, projects retained evidence/allowlisted qualification history and safe journey progress (`research.ts:14–218`). Feature evidence statements are intended feature-owned business content; their presence is not a leak through generic journey storage. No raw evaluator payload or hidden reasoning was observed in that projection. Inspecting calls does not perform a recovery write.
- **Future authority:** `runForFuture` is a read-only validated effective-authority projection (`futureWorkPropagation.ts:13–28`), not a latest unrelated run lookup or mutation. Recovery updates the appropriate futureProgrammeRevision versus programmeRevision fields. Preservation of all future-binding combinations still requires more than these source reads.
